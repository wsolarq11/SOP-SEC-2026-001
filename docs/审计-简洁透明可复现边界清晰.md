# 全仓「简洁 · 透明 · 可复现 · 边界清晰」四维审计

> 范围：整个 `SOP-SEC-2026-001` 仓库的**代码与文档语义**。
> 代码：`tools/**/*.py`、`tools/*.sh`、`.github/workflows/*.yml` 及其集成。
> 文档：`AGENTS.md`、`docs/*.md`、`sops/*.md`、`sop/*.md`、`sessionlogs/*`。
> 判定维度对齐 AGENTS.md 核心排序：简洁 > 透明 > 可复现 > 边界清晰。
> 基线：审查后文档层不达标项已就地整改（见 §4 整改清单）；代码层无必须回滚项。

## 总体结论

本仓库是一个**刻意保持单调、单一事实源驱动**的产线工具链，四维总体达标：

- **代码层四个维度均达标**。上轮 thermo-nuclear 评审（`THERMO-NUCLEAR-REVIEW.md`）已落地 7 项 canonical-helper 收敛，净删约 250 行；本次复核对齐后未见新的结构性问题。
- **文档层的『简洁 / 可复现』存在一种真实问题：数据漂移（drift）**——文档中硬编码的量化事实已与仓库实际状态分叉（见 §2.3、§2.4），且 AGENTS.md 未同步 `ship` 这条新增核心命令（见 §2.1）与新增的规范助手（见 §2.2）。
- **边界清晰是四个维度中最强的一项**：`registry.json` 唯一机器事实源、front matter/REGISTRY.md 单向生成、docx 不入库、`.publish-tokens` 不入库、命令统一入口 `kb.py`——边界与依赖方向在代码和文档里都写得很清楚、可交叉校验。

## 2 文档层：✅ 架构达标，两处实际发现需整改

### 2.1 【透明性·边界清晰】AGENTS.md 未同步 `kb.py ship` 与新增规范助手 (已修订)

`kb.py` 实现在 2026-08-31 已新增一键管线 `kb.py ship`（`tools/ship.sh`：同步→校验→测试→发布→commit/push，`set -euo pipefail` 失败即停、幂等）。它是当前**核心操作命令**，但：

- `AGENTS.md` 通篇 **0 处**出现 `ship`（§二、§七标准工作流均未提及）；
- `docs/项目事实与产线总览.md` 的命令表/依赖图（§2 等）也未列出 `ship`；
- 同期新增的规范助手 `tools/publish_tokens.py`（`.publish-tokens` 唯一读写端）与 `tools/lib.sh`（bash 路径样板共享库）亦未列入 `AGENTS.md` 仓库结构清单。

后果：读操作地图的新手按文档找不到一键发布入口，多个自然人/脚本对“统一入口”口径出现分歧——这正是「透明（可发现的语义）」与「边界清晰（唯一入口）」的双重削弱。

### 2.2 【透明】AGENTS.md 头部「最后核实」日期过期 (已修订)

`AGENTS.md` 首行标注“最后核实：2026-08-27”，但仓库状态已推进到 2026-08-31（`ship` 上线、全仓 thermo 整改落地、8 文档全量发布）。过期的时间戳削弱操作地图的可信度。

### 2.3 【可复现】文档硬编码的过期计数 (已修订)

`docs/产线化规划与评估.md`、`docs/项目事实与产线总览.md` 内硬编码了会漂移的量化计数，与仓库现状不符：

| 位置 | 声称 | 现状 |
| --- | --- | --- |
| `docs/产线化规划与评估.md` §3 表格“测试”行 | “当前 34 项” | `test_pipeline.py` 现为 **37** 项 test 方法（+`test_check_secrets`），上轮会话记录为 38 项通过 |
| `docs/产线化规划与评估.md` §3 文档登记 | “当前登记 7 条” | `sops/registry.json` 现为 **8** 条（含 SOP-DESK-2026-003、SOP-GEN-2026-004） |
| `docs/项目事实与产线总览.md` §3 活跃条目表 | “当前 registry 有 7 条” 且遗漏 SOP-DESK-2026-003、“最近发布”多为无 | `registry.json` 现为 **8** 条，且 8 条 `last_published_at` 均为 `2026-08-31` |

硬编码计数一旦不随状态更新即产生不可复现的文档。整改方向：**改为“以`kb.py test` / `sops/registry.json` 实际输出为准”**，或更新为当前真实值，避免手工二次维护同一数字。`docs/产线词表.md` 无硬编码计数，仅需在“验收一条线”补一句 `ship` 可选入口。

### 2.4 其余文档（✅ 达标）

- `docs/项目事实与产线总览.md`：事实模型/数据形态/依赖方向/已通线路/边界，一条线贯穿，`registry.json` 唯一权威、`check_docs / registry_render / ...` 分层依赖，边界清晰（除 §2.1 需补 `ship` 外）。

## 5 后续决策：CI 发布剪除（2026-09-01）

本次审计后复核发布/备份是否依赖 CI，查证 GitHub Actions 基线后作出**边界收敛**决策：

**事实基线（gh 查证）**
- SOP Publish Pipeline（`publish.yml`）自 08-28 起历次 push 全部 **failure**，根因：CI 还原的 `PUBLISH_TOKENS_B64` 缺 `SOP-DESK-2026-003` 的 token → 在 token 完备性校验处中断，**从未真正发布成功过**。
- `test.yml` 历次全绿。
- 线上 docx 全部由**本机 `ship`/`publish`** 发布，发布历史 `publish-history.jsonl` 无 CI 发布记录。

**决策**
- 删除 `.github/workflows/publish.yml`：CI 不再真发布，避免“CI 发布无即时结果 + `PUBLISH_TOKENS_B64` secret 漂移”这一不可复现/不透明源。
- CI 只保留 `test.yml`（`kb.py test` + `line`）作只读回归校验门：无发布副作用、无需 token、可即时看结果。
- 发布唯一入口 = 本机 `ship`/`publish`（构建→校验→上传→写记录→commit/push），结果当场可见。
- 备份（飞书 bundle = 本机 pre-push hook）本就不依赖 CI，保持不变。
- 删除失效 GitHub secrets `PUBLISH_TOKENS_B64` / `LARK_APP_ID` / `LARK_APP_SECRET`（仅原 publish.yml 使用，用户确认清除）。
- 移除 `token_bootstrap.py` 中已无消费者的 `--sync-secret` 及其 `_repo_name`/`_sync_ci_secret` 死代码（同时清理 `import base64`）。
- 同步更新 `AGENTS.md`、`docs/项目事实与产线总览.md`、`docs/产线化规划与评估.md` 的 CI 口径与 secret 提及。

**边界（改动后）**
| 动作 | 归属 |
| --- | --- |
| docx 发布 + 发布事实回写 | 本机 `ship` / `publish`（唯一） |
| 飞书 bundle 备份 | 本机 pre-push / post-commit hook |
| 回归/校验门 | CI `test.yml`（只读） |
| GitHub 同步 | 本机 `git push`；CI 只读校验 |
| GitHub secrets | 无（已清理三个失效 CI secret） |
