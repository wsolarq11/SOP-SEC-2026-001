# 项目事实、依赖与产线总览

> 本文档把 SOP 知识库项目的事实模型、数据形态和已通线路整编成一条自然依赖链。事实源只有 `sops/registry.json`；front matter、REGISTRY.md 由它单向生成；发布事实由仓库内安全摘要和仓库外带 token 日志共同承载。统一入口是 `python tools/kb.py`，统一观测是 `python tools/kb.py line`。
> 追溯文档：`docs/产线化规划与评估.md`（路线与验收）、`docs/产线词表.md`（口径词表）、`AGENTS.md`（仓库操作地图）。

## 1 一条线

项目只有一条链。文档之外的工具、CI、hooks 不是并列资产，而是这条链上某个节点的依赖或自动化。

```text
需求/变更
  -> 源事实：md 内容 + registry.json 登记
  -> 契约校验：check / registry-render
  -> 构建：docx 生成器
  -> 发布：publish.sh 同名覆盖飞书
  -> 记录：publish-history.jsonl + last_published_at
  -> 观测：kb.py line
  -> 备份：GitHub + 飞书 bundle
```

当前只有 1 条产出线：SOP 文档产出线。`document_id` 是产出单元，`sops/registry.json` 是机器唯一权威；不另建第二套台账、看板或数据库。

## 2 依赖方向

```text
决策/需求（人工、会话、工单）
   ↓ 形成文档意图
md 源（front matter 是文档自带契约）
   ↓ 登记
sops/registry.json（唯一机器源）
   ↓ 被读
registry_lib / check_docs / registry_render / registry_manifest
   ↓ 被调用
kb.py（根入口）
   ↓ 被触发
publish.sh / fact_ops / token_bootstrap
   ↓ 执行
sop_to_docx_stdlib -> lark-cli 上传 -> publish_log
   ↓ 被读
line_report
   ↓ 被触发
CI / git hooks / backup_commit
```

依赖规则：

- `sops/registry.json` 是唯一事实源；`REGISTRY.md` 和源文件 front matter 都是它生成的审计/契约视图，不反向依赖。
- `registry-render --write` 是 front matter 与 REGISTRY.md 的唯一同步器；`fact` 只写 registry，不再双写 front matter。
- `tools/kb.py` 是唯一命令入口；`check / test / publish / line / fact / token-bootstrap / backup / auth / cleanup` 都从这里触发。
- `tools/registry_lib.py` 是所有 registry 读写的共享依赖；`check_docs.py`、`registry_render.py`、`registry_manifest.py`、`publish_log.py`、`fact_ops.py`、`line_report.py`、`token_bootstrap.py` 都依赖它。
- `tools/publish.sh` 是发布链的执行节点，依赖 `check_docs.py`、`check_secrets.py`、`registry_manifest.py`、`sop_to_docx_stdlib.py`、`lark_json.py`、`.publish-tokens`、`publish_log.py`；它不引入第二套清单。
- `tools/publish_log.py` 只写真实发布事件，并回写 registry 的 `last_published_at`；仓库内 `sops/publish-history.jsonl` 只放不含 token 的事件摘要，仓库外日志保留 file_token。`line_report.py` 只读它们，不写。
- `.github/workflows/` 和 `.git/hooks/` 不产生新逻辑，只自动触发 `kb.py` / `publish.sh` / `backup_commit.sh`。
- `sessionlogs/`、`.trellis/workspace/`、`.trellis/tasks/` 记录过程事实，不参与发布数据流。
- `tools/feishu_preview_proxy/` 只辅助本机查看线上 docx，不参与发布链。

## 3 事实模型

| 事实类别 | 字段 | 承载位置 |
| --- | --- | --- |
| 产出单元 | `document_id` | registry 权威，front matter/发布历史为生成视图 |
| 文档契约 | `title / doc_type / domain / version / author / status` | registry 权威，front matter 为生成视图 |
| 落位契约 | `source / target_dir` | registry 独占 |
| 需求事实 | `requirement_ref` | registry 权威，front matter 为生成视图 |
| 审签事实 | `reviewer / reviewed_at / approver / effective_date / approved_at` | registry 权威，front matter 为生成视图 |
| 发布事实 | `last_published_at` 索引 + 发布事件 | registry 索引、`sops/publish-history.jsonl`、仓库外 JSONL |
| 上线事实 | `.publish-tokens` 中的 file token | 仓库外 gitignore 文件 |

状态语义：

- `status` 只有 `Draft` 和 `Approved`。
- `Draft` 可发布，但不代表已签批。
- `Approved` 才是已签批状态。
- 退役文档直接从 registry 删除，编号保留在 git 历史，不回收、不重用。

## 4 数据形态

### 4.1 registry.json

顶层为 `schema_version + entries`；每条 entry 允许 `document_id / title / doc_type / domain / version / author / status / source / target_dir`，可选 `requirement_ref / approver / effective_date / reviewer / reviewed_at / approved_at / last_published_at`。

### 4.2 md front matter

front matter 由 `registry-render --write` 从 registry 单向生成，禁止手工修改事实字段。必填 `document_id / title / category / doc_type / version / status / author / approver`；registry 有值时同步 `effective_date / requirement_ref / reviewer / reviewed_at / approved_at`。`category` 映射 registry 的 `domain`；`last_published_at` 只登记在 registry，不写入 front matter。

### 4.3 发布日志 JSONL

真实发布事件同时写两份：

- 仓库外 `%TEMP%` / 用户级日志：完整字段 `document_id / version / source / commit / dirty / source_hash / time / result / file_token`，不提交 git。
- 仓库内 `sops/publish-history.jsonl`：同一事件去掉 `file_token` 的安全摘要，随发布事实一起提交，供跨机器审计。

### 4.4 .publish-tokens

gitignore 本地配置，不入库；普通行 `source|md token|docx token`，备份行 `BACKUP_*|token|NONE`。文档中不输出 token 值。

### 4.5 line 报告

`kb.py line --json` 输出 `summary + entries`；`stage` 由发布记录、`Approved`、`approver` 推导；`blocked` 由源文件缺失、token 缺失或最新失败记录推导。

## 5 已通线路

### 5.1 起草与登记

1. 新建或修改 `sops/*.md`，会话/治理类可放 `sop/*.md`。
2. 在 `sops/registry.json` 登记 `document_id`，编号格式 `SOP-<域名>-<年>-<序号>`。
3. 运行 `python tools/kb.py registry-render --write` 同步 `sops/REGISTRY.md` 和全部源文件 front matter。
4. 用 `python tools/kb.py fact link|review|signoff|sync` 登记需求、评审、签批事实；工具只写 registry，再由 renderer 单向同步 front matter，不伪造签批。

### 5.2 校验与构建

- `python tools/kb.py check`：校验 front matter、registry 契约、REGISTRY.md 和源文件状态。
- `python tools/kb.py test`：回归生成器、registry、发布日志、事实命令、token 自举、产线报告和敏感扫描。
- `python tools/kb.py publish --dry-run`：生成清单、检查 token、构建 docx，不上传、不写日志。
- `python tools/kb.py publish --bootstrap`：缺 token 时自动首次上传并登记。

### 5.3 发布与记录

`tools/publish.sh` 按构建、校验、发布、报告四步执行；真实上传成功后，`publish_log.py` 写入仓库外完整日志和仓库内安全摘要，并回写 `last_published_at`，再同步 REGISTRY.md 与 front matter。`--dry-run` 无副作用。

### 5.4 自动化与备份

- CI：`push` 后 `.github/workflows/test.yml` 跑回归，`.github/workflows/publish.yml` 校验、构建、发布，并在发布后把 `last_published_at`、REGISTRY.md 和安全发布摘要提交回 master。
- hooks：`pre-commit` 跑敏感扫描，`post-commit` / `pre-push` 跑凭据守卫、敏感扫描和飞书 bundle 备份。
- 备份：`backup_commit.sh` 创建完整 git bundle 并同名覆盖上传；GitHub remote 与飞书 bundle 为双备份。
- 初始化：`python tools/kb.py backup --install`，再 `--init --wiki-token <90目录wiki node_token>`。

### 5.5 观测

`python tools/kb.py line [--doc <document_id>] [--json]` 只读 registry、front matter、发布日志和 token 完备性，输出状态分布、发布记录数、最近发布与阻塞项，不输出 token。

非文档资产不另设观测线；它们的健康状态由同一入口验证：`check` 管契约，`test` 管回归，`publish --dry-run` 管发布链，`backup --dry-run` 管备份链，CI 管自动化执行。

## 6 验收与自检

```bash
python tools/kb.py check
python tools/kb.py test
python tools/kb.py publish --dry-run
python tools/kb.py line --json
python tools/kb.py line --doc SOP-GEN-2026-004
python tools/kb.py backup --dry-run
```

最小验收样本：

1. `SOP-GEN-2026-004` 登记在 registry。
2. 真实首次上传后登记 `.publish-tokens`。
3. `publish` 同名覆盖成功并写入发布日志。
4. registry 回写 `last_published_at`。
5. `line --doc SOP-GEN-2026-004` 显示“已发布”且无阻塞。
6. `check`、`test`、`publish --dry-run` 通过，工具链和自动化按同一依赖链可重复验证。

## 7 边界

- `.docx` 不允许进入工作区；生成和发布文件只放 `%TEMP%\sop-exports\publish\`。
- 带 token 的发布日志、`.publish-tokens`、CI 凭据不提交 git；`sops/publish-history.jsonl` 只放不含 token 的安全摘要。
- 本仓库只维护 1 条产出线，不引入任务系统、看板或新数据库；Trellis 只作为过程记录，不替代 registry。
- 当前活动文档保持 `Draft`；`approver / effective_date / reviewer / approved_at` 待真实签批后填写。
- Trellis scripts/skills 属于上游模板运行时，不重写以避免 `trellis update` 覆盖。
