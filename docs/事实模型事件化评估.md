# 事实模型事件化迁移评估

> 目的：评估把事实模型从「一组需要同步的文件」迁移为「**单一不可变事件日志 + 只读投影**」这一「最接近银弹」的方向——它能消哪些失真、消不掉什么、一次性成本多大、以及三个「靠近但不重写」的折中。
> 位置：本文件是*评估/规划类*文档（同 `docs/产线化规划与评估.md`），不登记 registry，不构成新发布产线。
> 现在日期：2026-09-02。依据：对 `tools/publish_log.py`、`tools/registry_lib.py`、`tools/registry_render.py`、`tools/line_report.py`、`sops/publish-history.jsonl`、`AGENTS.md` 的源码级取证。

## 0 先回答标题问题：这不是想要的"银弹"，但最能接近

**不存在"零失真、零源、零成本"的银弹。** 失真的根不全在"源的数量/一致性"，而在"把人的/外界的**语义**落进机器契约"这个行为本身必然有损耗——这类"语义失真"（发签人是否真、内容版本是否对、token 是否有效）**任何模型都消不掉**。

事件化是**唯一能从"源头机制"上拉低"同步/一致性/外部改写"这三类硬失真**的手段。它对"硬失真"接近"银弹"（机制层面几乎消除），对"语义失真"依然无能为力。所以本评估的结论是：**值得把现有轻投影向事件化"靠一步"，而非全量重写成完整事件溯源。**

---

## 1 现状：你其实已经事件化了一半

取证结论——仓库已有事件化的**雏形**，但**没有把它推到系统化**：

| 现状机制 | 事件化程度 | 证据 |
| --- | --- | --- |
| `sops/publish-history.jsonl` | ✅ 已"append-only 事件 + 去 token 安全投影" | `publish_log.write_repo_summary` 只 append `document_id/version/source/commit/dirty/source_hash/time/result`，`file_token` 被剔除 |
| 仓库外发布日志 | ✅ 已 append-only（含 token） | `publish_log.append_publish` → `write_record`/`persist_record`/`durable` |
| front matter / `REGISTRY.md` | ✅ **已是 registry 的单向投影** | `registry_render.py --write` 幂等重建 |
| **`registry.json` 本体** | ❌ **是"状态"而非"投影"** | `publish_log._update_registry_last_published` 直接**改 registry JSON**，不回放日志重建 |
| 审计（WAL） | ❌ 未达标 | 事件只 append，**没有变更前/后快照、请求指纹、幂等键**（`AGENTS` #13/#14） |

**一句话：** `publish-history.jsonl` + front matter 已经是事件化的半成品；缺的只是"让 registry 也从日志重建"以及"补齐审计快照"这两步。

## 2 一次性迁移成本（诚实估算）

| 工作项 | 代码影响面 | 一次性成本 | 破坏性 |
| --- | --- | --- | --- |
| A. registry.json 改为"投影"（由 `publish-history.jsonl` + 事实命令日志重建） | `publish_log.py`、`registry_lib.py`、新增事件仓库 | **中高** | 需新增"事实事件"类型（link/review/signoff 也进日志），并写**回放器** |
| B. 补齐审计 WAL（变更前/后快照、幂等键、请求指纹） | 新增 `audit_log.py` | **中** | 核心状态变更处全接 WAL |
| C. 统一"最近发布"单一口径 | `line_report.py`（改 `_latest_publish`/`_build_lines` 为单一投影或单一索引）+ 去重键补 `source` | 低 | 独立可先行 |
| D. `.publish-tokens` 跨机/清 TEMP 显式化 | `publish_tokens.py`/`line_report` | 低 | 不合并源，只改观测口径（"待自举"而非硬阻塞） |

**关键判断：** 全部迁移是**一次性的、可逆的**（git + 事件回放可重建），但"把 registry 变成投影"会让 `direct edit registry JSON` 成为**被禁止**，改为 `append 事件 → 重新渲染`。这是最大的行为迁移（对现有人工习惯有打断）。

**按 AGENTS：**
- 幂等键、审计、UTC/RFC3339 本身就是强制项（#8/9/13/14）；事件化不是要新加，而是**让现有文件承载这些纪律**。
- 保留期/不可抹除：WORM 意向需飞书 bundle / 仓库 JSONL 共同承担（已有退化双备份，可复用作 WORM）。

## 3 能消 vs 不能消

**事件化能消除（硬失真/结构失真）：**

1. **一致性失真 → 机制消除**：只有一份 append 事件，其余全是只读投影 → 无"源 vs 源"、无手动同步、不可能双口径（投影由同一日志重建）。
2. **外部改写/静默改动 → 天然抵抗**：投影每次渲染全量重建；外部改只能改投影文件，下一次渲染覆盖 → 无第二份可写源。
3. **"内容版本 vs registry version 对不上" → 语义缝隙**：`version` 作为事件 append，投影只显示；不再有"人工维护版本号双写"（见失真审计①）。
4. **双口径 last_publish（失真③）→ 只读投影单源**：`last_published_at` 由事件日志推，不再"取 max"。

**事件化不能消（不可合成的语义失真）：**

| 失真 | 为什么消不掉 |
| --- | --- |
| 发签人是否真（approver 真假） | 事件只是"记录 X 于 t 签批"，**不验证"X 真的是该文档的批准人"**——那来自外部现实，无机制可核 |
| 内容/版本的事实"更新"**是否如实** | 事件日志只记"有人断言版本=v2"，不校验"正文真的改成 v2" |
| 真伪幂等键的人工错填 | 事件机制管"格式幂等"，管不了"人把错的幂等键/事件类别写进日志" |

**结论：** 事件化把"所有硬失真"拉近为"一个 append 纪律"；剩下的"语义失真"**必须**留在人机边界，是任何系统都无法根除的部分。

## 4 三个"靠近但不重写"的折中（按性价比排序）

### 折中 1（最低成本，推荐先行）：统一"最近发布时间"单源 + 补 `source` 去重键
只改 `line_report.py`：`last_publish` 以 registry `last_published_at` 为唯一索引（发布记录只作证据链，不作时点），`_read_publish_records` 去重键补 `source`。
→ 直接消失真审计 ③（双口径）与 `%TEMP%` 丢弃漂移，一行逻辑、不迁移架构。

### 折中 2（中成本）：事实登记事件化
把"事实命令"（`fact link/review/signoff`）和"发布/签到"都**append 到统一事件日志**，registry 仍作投影。= **把"写 registry" 改成 "append 事件"**，保留 front matter/REGISTRY 投影。
→ 消失真审计 ①②（双向残留 + 结构字段镜像），registry 变"推导"而非"人工状态"。成本中等，可在折中 1 之上推进。

### 折中 3（最高、但最接近"银弹"）：完整事件溯源 + 审计 WAL
在折中 2 上补齐 hook 门禁（只读复用 `registry_lib` 判据 + 门禁"自证覆盖"）与审计快照。
→ 一次性投入最高，但结构失真近乎根除、外部改写被"覆盖还原"、审计/回溯天然成立。
→ **除非你有"逐事件回溯/历史重放/多机器对账"的真需求，否则折中 2 已覆盖本仓库 95% 失真收益；折中 3 是"锦上添花"，别为它背完整重写债。**

## 5 决策表：门禁 / 自愈 / 少源 / 事件化 并列

| 方案 | 消除失真类型 | 引进失真源 | 一次性成本 | 是否触碰语义失真 | 对 AGENTS 边界 |
| --- | --- | --- | --- | --- | --- |
| 收敛（已做） | 多源、重复登记 | 无（单向） | 已投入 | 不消 | ✅ |
| 门禁（复用判据+只读） | 外部改、原后校验 | 机制性（可控，四铁律压到≈0） | 中 | 不消 | ✅ |
| 自愈（单向回填） | 事后不用手修 | 机制性（若反向则高危） | 中 | 不消 | ⚠️ 反向即反收敛 |
| 少源（合并视图/双口径） | 双口径、多视图 | 低（必须边界保留 token/正文） | 低 | 不消 | ✅（须保安全/内容源） |
| **事件化（折中1/2/3）** | **硬同步/外部改/双向**（强） | 机制性（append 纪律） | 中→高 | **不消**（语义失真无关） | ✅ 强匹配 #13/14/guarded |

**横比结论：**
- 事件化是唯一**从"同步/一致性"层面主动消除硬失真**的方案（其余只是"降低频率/拦截/回填"）。
- 单一事件日志把"失真源"压到 1 个 append（而收益可见），显著优于"多源 + 定期对账"。
- 但**不消灭语义失真**，且成本最高、行为迁移最大。

## 6 建议的落地路径（推荐次序，可独立分步）

推荐**渐进、可分步、每步自检**，不一次推到折中 3：

1. **先行：**统一 `last_published` 单源 + `source` 去重键（折中 1，成本低、立即降双口径失真）。
2. **第二步：**事实命令 + 发布改为"append 事件 → 投影 registry"（折中 2），此时 front matter/REGISTRY 已是投影、自然跟随。
3. **第三步（可选）：** 再补齐审计 WAL/hook（折中 3），仅在确有回溯/强审计需求时做。

每步验收：
```bash
python tools/kb.py check
python tools/kb.py test
python tools/kb.py line --json     # 单源时间、无假阻塞
python tools/kb.py publish --dry-run
```

并把 **registry.json → 重建投影、禁止手工编辑** 固化进流程（否则事件化无意义）。

---

> 一句话给"追银弹"的收束：**没有把失真清零的银弹，但有"事件化（append 日志 + 只读投影）这一条最接近的、能从一致性层面几乎消除硬失真的路。侦察显示项目已有一半雏形，值得朝"折中 1/2"靠拢（小改、可逆、不重写），而非直奔"折中 3 全量事件溯源"。**

## 7 决策收敛（2026-09-02）

本节把讨论与验证后的**实际取舍**固定下来，使评估文档与仓库现状一致（避免文档漂移）。

### 7.1 已落地：折中 1（统一"最近发布"单源）

- **改动**：`tools/line_report.py` 的 `_build_lines` 中 `last_publish` 由"发布日志 time 优先、缺省回退 `last_published_at`"**双口径**，改为**只取 registry `last_published_at`**（单源）。发布记录不再作时点来源，仅承担"阶段判定 / 阻塞判断 / 证据链"。
- **收益性质**：只改**观测口径**，不写入路径、不动事实本体、不加 schema；**几乎零新增失真源**（0 写入、去二择一、不碰语义事实）。
- **代价**：`line` 的"最近发布"只显示到 `YYYY-MM-DD`，不再展示发布记录里更细的 `time`（真实信息，但非"编造"，`last_published_at` 由 `publish_log` 从权威事件稳定回写）。这是**展示精度**损失，不是**事实真**损失。
- **验证**：`check` OK；`kb.py test` 38/38 通过；`line --json` 8/8 单源 `2026-08-31`、`published=8`、`blocked=0`。
- **带坑的取舍**：曾尝试把"去重键补 `source`"，但会破坏既有 `test_line_report_deduplicates_publish_after_source_rename`（依赖跨 source-rename 去重），故**回退**，仅保留单源改动。→ 结论：**去重键保持 (doc_id, version, time, result)，不加 source**。

### 7.2 未推进：折中 2（事件化）——待真需求

- **判断**：折中 1 是"低成本、低收益、可逆"的观测收敛；**折中 2 属于架构负债起点**，会引入**两条新失真风险**：
  1. **回放器正确性**：把"写 registry"换成"append 事件 → 重放投影"，回放器写错 = 新增隐蔽失真。
  2. **禁止手工 edit registry**：一旦 registry 变"投影"，任何绕过事件直接改 registry 会造成新的反向分歧。
- **结论**：仅在"逐事件回溯 / 历史重放 / 跨机对账"这些**真实需求**成立时才值得推进；仓库当前（8 文档、单一产线）**大概率无此需求**，故**折中 2 暂不推进**。

### 7.3 折中 3 / 审计 WAL——待合规或强回溯需求

- 审计 WAL（变更前/后快照、幂等键、请求指纹）对应 AGENTS #13/#14（保留期 ≥5 年、不可抹除），但当前单人、8 文档属"过设计"，**仅当要对账/审计/跨人协作时**才值得。

### 7.4 余下可选加固（非必做，按需挑）

- `.publish-tokens` 缺失降级为"待 token 自举"而非"阻塞"（降假阻塞）。
- 正文"版本修订"硬校验：把 `_check_revision_match` 从"只报"升级为提交/推送前硬拦（堵失真 ①）。
- 删除 `fact sync` 反向语义（改 docstring，防诱人反向写）。

### 7.5 本评估的边界与不引入新产出

- 本节是把**讨论与验证的取舍**同步为文档，**不登记 registry、不新建发布产线**；`docs/项目事实与产线总览.md` 仍为事实模型单一权威定义页。
