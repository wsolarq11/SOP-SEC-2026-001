# 事实模型失真审计

> 目的：把「事实模型总是感觉容易失真/漂移」这一体感，落成一份**逐项带证据**的失真源清单，作为后续「收敛到哪一层 / 补哪几个洞」的决策输入。
> 方法：对事实模型涉及的全部事实源（`sops/registry.json`、front matter、`sops/REGISTRY.md`、发布日志、`.publish-tokens`、sessionlogs）逐一取证，不漏掉任何一处「双源 / 反向写 / 人工维护 / 本地暂存」的缝隙。
> 现在日期：2026-09-02（以源码与库存量抽查为准）。
> 事实源唯一权威：`sops/registry.json`（`docs/项目事实与产线总览.md` §3、`AGENTS.md`）。

## 0 结论先行

**不是重构，是收敛收窄到「内容事实层」并堵掉 3 处残留缝隙。**

- 当前结构事实层（`registry.json` ⇄ front matter ⇄ `REGISTRY.md`）已经**单向、唯一权威**收敛完成，`check`/`test` 能兜住结构层的大多数漂移。**这一层不该重构**——移动/重命名字段只会引入迁移成本与新的不一致窗口，不解决漂移。
- 用户感觉「容易失真/漂移」的根，来自收敛只做到**结构层**、没到**内容事实层**，外加几处**残留双写/多口径/本地暂存**。这些是「收敛未收净」，不是模型设计错误。
- 修补优先级：先补「内容事实没有权威」与「`fact sync` 反向语义残留」，再统一「最近发布时间」口径，最后把本地 `.publish-tokens` 的跨机漂移窗口文档化/显式化。全部是**小改动、不重构 schema**。

---

## 1 失真源清单（含证据）

按「承载位置 × 漂移机制 × 影响 × 修补归属」排列。**①-③ 是高优先（直接产生可见失真）；④ 是结构性空隙；⑤⑥ 是已收敛但残留的缝隙。**

### ① 内容事实：版本 / 修订记录没有单一权威（最高优先）

- 机制：`registry.json` 只登记结构字段（`version / title / ...`），**不登记文档正文内容及其版本修订**。正文 `## 版本修订记录`（`registry_lib.py` `VERSION_HEADING`）由**人工在 md 里维护**。
- 证据：
  - `registry_lib.py` L370-378 `_check_revision_match`：专门校验「front matter `version` == 正文 `## 版本修订记录` 最新版」，**不相等即报 FAIL**。这条检查之所以存在，正是因为它常被打破——人工改正文不改 front matter/registry，机器事后才发现。
  - `docs/AGENTS.md`「版本修订记录惯例」：版本号与修订记录**由人工维护**，自动化不写。
- 漂移机制：人工在正文改版本/内容，结构元数据（registry/front matter）不会自动跟进 → `check` 报 `version 与修订记录不一致` 或内容与登记 title/版本脱节。
- 影响：**内容事实失真**——看 registry 是 v1.0，正文其实已改到 v1.2 的说不上；`last_published` 与该内容是否**已发布**脱节。
- 修补归属：**收敛边界推进到「内容事实」**——让「本期源文件是什么、hash 是多少、发布的是哪一版」成为 registry/发布记录可推导的判定。`publish_log.py` 已写 `source_hash`，缺的是「用 hash/正文变化驱动 version/title 再发布」的闭合（见 §2 建议 1）。

### ② 反向写残留：`fact sync` 的旧语义（高优先，反收敛）

- **证据**：`tools/fact_ops.py` L122 docstring 仍是 `sync ... copy front matter facts to registry`（**反向复制**）——与「front matter 是 registry 单向生成视图、不再反写」的新契约**自相矛盾**。
  实际实现 `cmd_sync`（L94-103）只调 `registry_render.main(["--write"])`（已是正向写），**代码行为新、docstring 旧**。
- 漂移机制：文档/工具注释是「旧语义出口」，会**诱人后续按反向思路补逻辑**（有人看到说明以为允许反写 front matter），是漂移的内生温床。
- 影响：低（行为未反写），但**契约表达失真**，诱因性高。
- 修补归属：**改 docstring/帮助文本为「从 registry 单向重新生成 front matter」，删掉/废弃 `sync` 反向语义**（或合并进 renderer）。

### ③ 发布时间双口径：`line` 的 `last_publish` 取 max（高优先）

- **证据**：`line_report.py` `_latest_publish`（L75-84）从发布日志按 `source` 过滤 `result==success` 取 `max(time)`；`_build_lines`（L138-139）若发布日志有记录取日志 `time`，否则回退 `entry["last_published_at"]`。而 `产线词表.md` L16 也写「优先取发布日志最大 time，缺失取 registry last_published_at」。
  - 同类：`line_report` 从 **4 个日志路径**（`default_log_path / repo_history / durable / legacy_temp`）合并去重（L35-63），去重键 `(document_id, version, time, result)` **不含 `source`**。
- 漂移机制：发布事实分散在 4 处（含 `%TEMP%` 下的 `legacy_temp_log_path`）＋ registry 索引，`line` 对两口径取 `max`/回退——一旦任一处与 registry 不一致，报告就与 registry/产线**视觉漂移**。
- 影响：观测（`line`）与实际事实可能不符；`TEMP` 被清（AGENTS 明言可能被清空）后**丢失普通日志**，只剩 durable + repo 摘要。
- 修补归属：**统一单一口径**——「最近发布 = registry `last_published_at` 索引（发布记录只作证据链，不作时点）」或「repo 摘要为主、其余为溯源码」。修 `_read_publish_records` 去重键补 `source`。

### ④ 上线事实 `.publish-tokens`：本地态，跨机/清 TEMP 有窗口（结构性空隙）

- **证据**：`.publish-tokens` 是 gitignore 本地文件（AGENTS.md §五、`docs/项目事实与产线总览.md` §4.4）；`publish_tokens.py` 的 `read_publish_tokens` 读不到返回空 dict（L31-33）；缺失时 `line_report._is_blocked`（L114）把无 token 判为 `阻塞`。`token-bootstrap` 负责自动补，但其目标是仓库外受控文件。
- 漂移机制：该文件**不入库**，换机器/换账号/清仓库都不存在 → `line` 显示阻塞，即便线上已发布。它的「事实」与文档发布事实**不同步**。
- 影响：跨机器审计/恢复时，`line` 的 `blocked` 与真实上线状态会**漂移**（假阻塞）。
- 修补归属：**document 它把「上线事实」也归并到可推导口径**——例如 `.publish-tokens` 缺失时 `line` 记为「待 token 自举」而非硬「阻塞」，或把 token 自举纳入 ship 入口（AGENTS 已说 `token-bootstrap`），此处只需**文档+观测口径一致**，不必改 schema。

### ⑤ 结构事实层：已收敛，但有可查窗口（已加固，低风险）

- **证据**：
  - `registry_render.py` front matter「必填 `document_id/title/category/doc_type/version/status/author/approver`；registry 有值才同步可选事实」= **单向**（registry→fm）。
  - `check_docs.py`/`registry_lib.py` 一致性校验（L387-401 `FRONT_MATTER_MATCH` / `FRONT_MATTER_OPTIONAL_MATCH`、L404 `_check_optional_field_shapes`）。
  - 历史失真源：`check_docs.py` L6 注明「2026-08-14 规文源文件曾被外部进程改写（front matter丢字段）」——**这正是收敛之所以存在的理由**。
- 修补归属：已收敛，无需改。**保留 `check`/`registry-render --write` 为唯一同步器**；不要新增手工反写入口。

### ⑥ 过程事实：sessionlogs / `.trellis` 不参与数据流（观测缺口，不参与收敛）

- **证据**：`总览.md` §2 L56「`sessionlogs/`、`.trellis/workspace/`、`.trellis/tasks/` 记录过程事实，不参与发布数据流」。
- 修补归属：**保持隔离**；需要时可把「决策/审签依据」显式 link 到 registry 的 `requirement_ref`（`fact link`），避免过程记录与 registry 描述分歧。非必改。

## 2 收敛建议（按优先级，均为小改、不重构 schema）

1. **给「内容事实」一个权威锚**：把「正文 `## 版本修订记录` 最新版 == registry `version`==front matter `version`」纳入 `check` 的**硬校验**（目前 `_check_revision_match` 已存在但只在 hash/`version` 角度；强化为「版本修订表必须由 registry-render 可推导或强制一致」），让「内容版本」与「登记版本」无法悄悄分手。→ 直接消「内容失真」。
2. **堵 `fact sync` 反向语义**：`fact_ops.py` L122 docstring 改回「由 registry 单向重新生成 front matter」，移除任何「front matter→registry」描述。→ 防止反向写被重引入。
3. **统一「最近发布时间」单口径**：`line_report._latest_publish` / `_build_lines` 建议以 **registry `last_published_at` 索引** 为准，发布记录只作证据；并给 `_read_publish_records` 去重键补 `source`。→ 消 §1 双口径与 `%TEMP%` 丢弃后的漂移。
4. **上线事实降级表达**：`.publish-tokens` 缺失时 `line` 输出「待 token 自举」而非「阻塞」（或把 token 自举纳入 `ship` 前置）。→ `line` 不再「假阻塞」漂移。
5. （加固）**人工维护版本修订**路径：确需人工改正文时，把「改正文→ `registry-render --write` → `check`」写成微流程，让 `version/修订` 有单一回归点。

## 3 不建议做的事（不重构的原因）

- **不要重构 schema**（改主键/字段枚举/存储架构）：突变对象为「内容↔结构不一致」「双口径时点」「本地暂存漂移」这些**正确性/一致性**问题，都不是「字段放哪」能修的；迁移制造新的不一致窗口，且与「单一权威」原则无益。
- **不要新增第二套台账/DB**：`AGENTS 维护唯一 registry`，再起一套只放大双源漂移。
- **不要允许 front matter↔registry 双向写**：那正是收敛前失真的成因，重构绝不倒退回双向。

## 3 验收（后续择洞修补后的自检）

修补任一项后，跑通：

```bash
python tools/kb.py check
python tools/kb.py test
python tools/kb.py line --json      # 校验 last_publish 口径是否单源、无假阻塞

```

并保证 `registry.json`、front matter、`REGISTRY.md`、发布摘要四者 `time/version` 一致（单源）。
