# 产线化规划与评估

> 状态：路线已定稿，阶段 0-4 与缺口闭环已实施；事实命令、token 自举、持久发布日志、CI 观测/日志接线完成；git 提交与推送作为部署动作待用户确认
> 范围：SOP 文档产出线，即“需求/变更 → 起草/登记 → 评审/签批 → 构建/发布 → 维护/归档”
> 原则：不重复造组件，先统一事实与流程，再固化口径，最后按需补观测工具

## 1 结论

本项目的基础产线组件已经基本齐全：registry 登记、md 源、健康检查、docx 构建、CI 自动发布、敏感扫描、git hooks、飞书 bundle 备份和回归测试都已存在。

当前真正缺的不是新的产线系统，而是把现有组件串成一条可解释、可评估的线，并且分三层统一：

- 事实层：每个产出单元有稳定编号、状态、源文件、需求来源、签批事实和发布事实。
- 流程层：所有文档走同一套阶段和闸门，而不是靠人临时判断。
- 口径层：对“在产、待审、已发布、阻塞、产线数”等词语和统计规则给出同一解释。

当前的具体断点是：需求入口没有统一编号和关联记录；审签只停留在 `Draft / Approved` 状态，没有签批时间和记录；发布成功与否主要留在 CI 或命令输出里，没有持久化发布记录；没有产线级汇总，无法一眼看到在途、待审、已发布、阻塞项。本轮已把这些断点接线：`requirement_ref` 全量回填、`fact` 命令提供评审/签批登记入口、发布日志持久化到用户目录并写回 `last_published_at`、`kb.py line` 统一观测。

**第一版不需要做看板、不需要新增产线台账文件、不需要引入新数据库。** 已实现轻量 `kb.py line` 作为统一观测入口；`sops/registry.json` 保持唯一中央台账。

## 1.1 统一顺序：先事实，再口径

“统一口径”不是第一步，也不是最后一步；它是对统一后事实的解释规则。真正要做的是三层一起收敛，第一版以“事实层最小化”为入口：

| 层 | 要统一的内容 | 当前状态 |
| --- | --- | --- |
| 事实层 | 每个产出单元有稳定 `document_id`、状态、源文件、需求来源、签批事实、发布事实 | registry 已全量回填需求来源；fact 命令提供需求/评审/签批登记；发布写回 `last_published_at` |
| 流程层 | 所有文档走同一阶段与闸门 | 起草/登记、token 自举、构建/发布、发布记录已统一；审签通过 `fact signoff` 登记 |
| 口径层 | “在产、待审、已发布、阻塞、产线数”等词语和统计规则一致 | 已固化于 `docs/产线词表.md`，line 按同一规则输出 |

顺序不是“先统一口径再统一其他”，而是先确定最小事实模型（数据形态），再固化口径；口径反过来校验事实模型够不够用。当前最小事实模型是：

`document_id + status + approver + effective_date + 发布记录`

扩展可选事实字段（见统一路线阶段 1）：

`requirement_ref + reviewer + reviewed_at + approved_at + last_published_at`

这个模型先由 `sops/registry.json` 承载，发布记录已由 `publish_log.py` 落地为仓库外 JSONL；不需要另建一套“口径库”。

## 2 现状产线图

```text
需求/变更
   ↓
起草/登记（sops/*.md + registry.json）
   ↓
评审/签批（front matter status + approver）
   ↓
构建/发布（tools/kb.py publish + GitHub Actions）
   ↓
维护/归档（版本修订、退役从 registry 删除）
```

当前自动化较强的是“起草/登记”到“构建/发布”这一段；前半段需求承接和后半段发布观测是断点。

## 4 断点与风险

| 断点 | 影响 | 处理状态 |
| --- | --- | --- |
| 需求无编号、无来源、无关联 | 无法追溯“为什么会有这份 SOP” | `requirement_ref` 已全量回填，`fact link` 提供登记入口 |
| `approver` 多为“待定” | 无法判断文档是否真正被业务签批 | `fact signoff` 提供真实签批登记；未签批不伪造 |
| Draft 和 Approved 都可发布 | 发布事实与签批状态混在一起 | 已固化口径：Draft 可发布，但不等同于已签批 |
| 发布记录不持久 | 无法统一观测最近发布时间和结果 | 发布记录同时写入 `%TEMP%` 发布快照、用户级持久日志，并写回 registry `last_published_at` |
| 没有产线汇总 | 只能逐文件看 registry 和 git | `kb.py line` 输出状态分布、发布记录、阻塞项 |
| 新文档缺 token 会卡住发布 | 首次上传需要人工补 token | `token-bootstrap` / `publish --bootstrap` 自动首次上传并登记 |
| CI 发布日志随 job 消失 | 无法核对 CI 发布结果 | CI 上传 `publish-log` artifact，并在 test/publish workflow 输出 line 报告 |

主要风险不是技术复杂度，而是“过度产线化”：为当前规模引入任务系统、看板、状态机或新台账，会让维护成本超过收益。

## 5 目标产线模型

统一以 `document_id` 作为产线产出单元，`sops/registry.json` 保持唯一机器来源，不另建第二套登记表。

| 产线阶段 | 当前对应物 | 观测口径 |
| --- | --- | --- |
| 需求/变更 | 对话、会议、工单、Trellis task | 不强制登记；需要追溯时再补需求记录 |
| 起草/登记 | `sops/*.md` + `registry.json` | registry 中已有条目即视为在产 |
| 评审/签批 | front matter `status` + `approver` | Draft = 未签批；Approved = 已签批 |
| 构建/发布 | `kb.py publish` / GitHub Actions | 发布成功事件写入发布日志，并写回 registry `last_published_at`；`--dry-run` 不写 |
| 维护/归档 | 版本修订；退役项从 registry 删除 | 历史编号保留在 git，不再出现在活跃清单 |

## 6 统一观测方案评估

| 方案 | 工作量 | 适用场景 | 状态 |
| --- | --- | --- | --- |
| 只定义口径和文档 | 小 | 当前规模 | 已完成 |
| `kb.py line` 命令行报告 | 半天 | 需要快速查看产线状态、阻塞项、发布记录 | 已实现 |
| registry 扩展可选字段 | 1-2 天含测试 | 需要需求追溯、负责人、签批时间 | 已实施并全量回填需求来源 |
| 新文档 token 自举 | 1 天含测试 | 新 SOP 首次上传不应依赖人工补 token | 已实现 `token-bootstrap` |
| 静态网页看板 | 更大 | 多角色需要随时查看 | 暂不建议 |
| 独立任务/数据库 | 最大 | 多产品线、复杂权限、跨系统集成 | 当前明确不做 |

**观测工具现状：已实现 `kb.py line`，不建看板。** 它只读 registry、源文件 front matter 和发布日志，不输出 token 或敏感信息。
