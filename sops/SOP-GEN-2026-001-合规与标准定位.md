# 合规与标准定位

> 本文件是知识库的**首篇参考说明（reference）**。它不规定具体怎么操作，只解释清楚一件事：我们为什么要关注 ISO 9001 / ISO/IEC 27001 / ISO/IEC 20000-1 这三套标准，以及它们和本知识库的关系。文档性质由 `doc_type` 区分，本库不强制登记 L1/L2/L3 层级。

## 一、先说一个底层事实：这三套都是"自愿认证"，不是法律

- ISO 9001、ISO/IEC 27001、ISO/IEC 20000-1 都是**自愿性管理体系认证**。没人（法律）强迫你做。
- 中国法律真正强制的是：网络安全等级保护（等保 2.0）、数据安全法、个人信息保护法等。它们和 ISO 体系是两套逻辑：一个是"必须合规"，一个是"自愿证明你做得好"。
- 所以"要不要满足"，**不取决于标准本身，而取决于三件事**：
  1. 客户 / 投标门槛（招标文件点名要某证）
  2. 行业监管要求（准入隐含要求）
  3. 你们自己的管理成熟度诉求（想降低风险、规范化运营）

> 一句话：标准是"加分 / 门票"，不是"红线"。

## 二、三套标准的现行版本

| 标准 | 管什么 | 现行版本 | 状态 / 注意 |
| --- | --- | --- | --- |
| ISO 9001 | 通用质量管理体系 | 2015 版 | 现行版本 |
| ISO/IEC 27001 | 信息安全管理体系 | 2022 版 | 2013 版已于 2025-10-31 失效，旧证一律作废 |
| ISO/IEC 20000-1 | IT 服务管理体系 | 2018 版 | 2023 确认有效，暂无换版压力 |

- 三者都包含 **2024 气候修正案**（治理层要求，与日常运维关系不大，知悉即可）。
- 三者共用 **HLS 高阶结构**（条款 4–10 一致）——这是能"整合"的前提，见第六节。

## 三、对"我们要不要满足"的判断

我们的画像：生产制造企业 + 甲方内部 IT + 有投标 / 监管准入诉求。

| 标准 | 判断 | 依据 |
| --- | --- | --- |
| **ISO 9001** | **必须满足（对标层）** | 生产制造 + 投标客户 + 监管准入。9001 是制造业最普遍的准入门票；它的过程方法、PDCA、SOP 受控，本就是知识库的骨架 |
| **ISO/IEC 27001** | **必须满足（对标层）** | 监管准入 + 敏感数据。我们之前评审的"安防平台人员变动 SOP"恰好是 27001 人力资源安全（任用终止 / 变更）的落地证据。等保 2.0 是法律强制，27001 是更成体系的自愿补充 |
| **ISO/IEC 20000-1** | **第二阶段再做** | 我们是甲方内部 IT，不是对外服务商，优先级低于前两者；除非投标明确点名要 IT 服务认证，再提前 |

**结论：9001 + 27001 是刚需对标，20000 是加分项。**

## 四、ISO/IEC 20000-1 的目标企业画像

**本质**：它认证的不是"产品"，而是你**持续交付和改进 IT 服务的过程**（规划、设计、转换、交付、改进）。所以"谁会做"完全取决于——你是不是一个 IT 服务的提供方（service provider）。标准甚至写明：认证对象可以是一家公司里的某个部门，不一定是独立公司。

**最典型的目标企业（对外交付 IT 服务）：**
1. **IT 外包 / 托管服务商（MSP）**：把运维、桌面、网络、数据中心托管卖给客户。招标时客户几乎必然要求 20000，是"你有正规服务管理体系"的背书。这是最硬核的持证群体。
2. **云服务商 / IDC / 数据中心**：提供 IaaS/PaaS/SaaS 或机房托管，金融、政企客户常要求"20000 + 27001"组合证书（服务规范 + 安全）。
3. **软硬件厂商的运维 / 客户成功部门**：卖产品同时卖持续支持服务，用 20000 证明支持服务可度量。
4. **已用 ITIL 实践、想让它"可审计"的组织**：20000 是让 ITIL 落地可被认证的自然路径（但标准框架中立，不强制 ITIL）。

**进阶但很常见的一类（与你们最相关）：大型甲方的内设 IT 共享中心。** 很多集团把 IT 部门按内部 service provider 运作——业务部门的内部客户有 SLA、有事件 / 变更流程。这类做 20000**不是为了对外投标，而是内部服务规范化、可度量、可改进**。我们"生产制造 + 甲方 IT"就属这一类：价值是内部治理，不是对外背书。

**不太适合 / 优先级低：**
- 纯产品研发、不交付持续性运维服务的公司 → 9001 更贴切。
- 小规模内部 IT、服务简单无 SLA 约束 → 投入产出比低，先对标、不认证即可。

**与 9001 怎么区分（制造场景易混）：** 9001 是通用质量，管"产品 / 服务"的生产质量（用它管制造质量）；20000 是 IT 服务这个细分领域的专项认证，管"IT 服务全生命周期"。一个制造企业完全可以**同时持两者**——9001 管生产、20000 管内部 IT——且因共用 HLS，能整合进同一个 IMS，不冲突。

**一个关键审核要点（如果将来真去做认证）：** 通过供应商链交付服务时，不能只甩一份供应商合同，必须证明你对链条各方（内部小组、外部供应商、分包商）的治理。这是 MSP / 外包场景认证审核里**最常见的不符合项来源**——提前在程序文件里写好"供应商治理"就不会踩坑。

## 五、顶级企业做法：整合管理体系 IMS

顶级企业不会建三套孤立体系，而是把三套认证做成**一个整合管理体系（IMS）**，用同一套文件覆盖重叠要求。

- **一套文件写一次**：9001 / 20000 / 27001 共用 HLS 高阶结构，很多控制项天然重叠（例如"变更管理"同时满足三个标准），一套文件覆盖即可，不重复写。
- **外部 IMS 常用三层文件**：L1 方针、L2 程序、L3 SOP + 记录。本知识库不把这些层级作为强制登记项；文档性质由 `doc_type`（policy / standard / procedure / guideline / reference）区分。
- **风险思维贯穿**：27001 的风险评估 + 9001 的风险思维，是体系的发动机，不是附件。
- **闭环治理**：内审 + 管理评审 + 持续改进（PDCA），否则体系会僵成"为了审核而写文档"。

> 我们当前进度：已有程序、规范和参考说明，缺方针类文档；是否需要补齐，等投标或认证触发后再定。

## 六、当前的位置与路线图

- **现在（继续建）**：按业务域沉淀作业程序、规范和参考说明；不在 registry 中登记文档与标准条款的映射。
- **中期（按需补充）**：如果将来要做认证，再按外部 IMS 要求补充方针和程序文件，形成"方针 → 程序 → SOP → 记录"受控链。
- **认证时机**：文件对标做好了，哪天投标要证，直接请审核机构来审即可，**不用返工**——这正是"对标实践"比"临时抱佛脚认证"省钱的地方。

## 七、与本知识库的关系

本库 SOP 按"企业 IT 职能域"归档，域名代码用于分类与编号；registry 只登记编号、类型、域名、目标目录，不登记文档与标准的映射。

| 域名 | 分类 | 说明 |
| --- | --- | --- |
| SEC | 信息安全 | 账号权限、合规审计、安全事件等 |
| APP / DESK | 应用与系统 / 终端与桌面 | IT 服务交付、事件、变更、SLA |
| INFRA / DR / GEN | 基础设施 / 容灾 / 通用 | 基础设施运维、容灾备份、跨域通用规范 |

## 八、待决策 / 开放问题

- **内容硬伤待补**（不在本总纲范围，但影响 27001 合规）：此前评审指出的——离职 SLA 最松、零合规条款、批准人空白。这恰好是 27001 审核会开不符合项的地方，补上即现成合规证据。
- **何时启动认证？** 触发点明确后再做：① 投标点名要某证；② 准备上 ITSM 平台把事件 / 变更 / SLA 真正跑起来。在此之前，维持"对标实践、不认证"即可。
